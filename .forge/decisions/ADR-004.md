# ADR-004: Separate Development Repo from Installable Template (Deferred)

## Decision

Keep `SSHRIHARI006/FORGE` as the development/research repo. When the `.forge/` contract stabilizes, extract a clean, reusable artifact into a second repo (e.g. `forge-template` / `forge-context`) containing only what gets installed into another project. Do not split prematurely.

## Context

The current repo is simultaneously two things: (1) where Forge itself is developed (`SPEC.md`, `FORGE_SPEC.md`, `tools/`, `tests/`, dev checkpoints/state), and (2) the Forge context that other projects should adopt (`.forge/` + living spec). A user cloning the public repo for adoption should get a clean starting point, not `SPEC.md`, `tests/`, `tools/`, or our development `state.md`/checkpoints. Conversely, template consumers must never leak their project state back into the template.

Target shape:

```text
forge-development (this repo)
       │
       │ build/release
       ▼
forge-template  (.forge/ + README only)
       │
       ▼
user's project (.forge/ installed)
```

with a dogfood loop: improve `INIT.md`/context in dev → publish template → agent uses it in a new project → issues flow back to dev.

## Alternatives

- Single repo serving both roles permanently (rejected: dev artifacts pollute the install path; dev `state.md` risks shipping as template content).
- Split immediately (rejected: architecture still in flux mid-TASK-008; extracting now would freeze an unvalidated contract and double maintenance during the pilot).
- Template as a subdirectory/subtree of the dev repo (reserved: possible release mechanism later, still requires the same clean-boundary decision).

## Reason

- Clean install path: adopters get `.forge/` + README, nothing else.
- The `.forge/` contract is unproven until the TASK-008/TASK-009 cross-agent drill passes; stabilizing first avoids publishing churn.
- Dogfooding the published template from this dev repo then becomes the real end-to-end test.
